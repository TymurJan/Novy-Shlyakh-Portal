4. **Сувора грантова чистота (De-commercialization):** Повне викорінення будь-яких комерційних модулів (тарифів, комісій, оплат у валюті). Платформа на 100% функціонує в межах безкоштовного соціального сервісу.

## 1. СПЕЦИФІКАЦІЯ РОЛЕЙ, ДИНАМІЧНИХ МАСОК ТА МАТРИЦЯ ДОСТУПУ

### 1.1. Ієрархія рівнів доступу (Access Levels)

```
[Рівень 1: Гість (Session_XYZ)]
       │
       ▼ (Підтвердження контакту: Telegram / IVR / SMS / Дія / ЦНАП)
[Рівень 2: Ветеран / Член родини] ──► (Базовий Кабінет, Тікети, Сейф)
       │
       ▼ (Активація статусу через КЕП/Меморандум)
[Рівень 3: Партнери (Динамічні маски)]
       ├── 🔹 Приватний фахівець (Pro-bono)
       ├── 🔹 Організація / БФ / ГО
       ├── 🔹 Державна установа / ЦНАП
       ├── 🔹 Роботодавець (Вакансії для ветеранів)
       ├── 🔹 Благодійник / Донатор
       └── 🔹 Освітній центр (Перекваліфікація, ваучери)
       │
       ▼ (Спеціальний адміністративний доступ)
[Рівень 4: Модератор / Координатор аналітики (ГО «Талан ЮА»)]
```

#### Рівень 1. «Гість» (Повна анонімність)
- **Сутність:** Будь-який неавторизований відвідувач.
- **Ідентифікація:** Віртуальний тимчасовий токен `Session_XYZ` (генерується у браузері, живе у `sessionStorage`/куках).
- **Доступ:** Відкрита база знань, покрокові гайди (ВЛК, МСЕК, пільги громад, перелік організацій).
- **Обмеження:** Приховані прямі контакти (телефони, email, прямі форми запиту). При спробі натиснути дію спрацьовує Soft-Gate модальне вікно.

#### Рівень 2. «Ветеран / Член родини»
- **Сутність:** Авторизована особа з підтвердженим ідентифікатором (Telegram ID або верифікований номер телефону).
- **Доступ:** Відкриття прямих контактів, створення запитів на консультацію, особистий кабінет, модуль «Історія справ», модуль «Захищений сейф документів».
- **Статус користувача (перемикач у профілі):**
  - `IS_VETERAN`: Пріоритет матеріалів ВЛК, демобілізація, УБД, протезування.
  - `IS_FAMILY_MEMBER`: Пріоритет психологічної підтримки сімей, оформлення довідок за військовослужбовця, юридичний супровід зниклих безвісти/полонених.

#### Рівень 3. «Партнери» (Єдина точка входу — адаптивний функціонал)
Партнерський акаунт є єдиною сутністю в базі даних, до якої підключаються незалежні бітові маски або списки активних статусів (`active_roles`):
- `ROLE_SPECIALIST`: Індивідуальний надавач послуг (психолог, юрист, реабілітолог). Працює за системою Offer/Accept.
- `ROLE_ORGANIZATION`: Громадська організація, благодійний фонд, хаб. Має профіль організації, може залучати кількох координаторів.
- `ROLE_STATE_BODY`: ЦНАП, відділ соцзахисту, орган місцевого самоврядування (ОМС). Може реєструвати кейси «з голосу» (від імені аналогових ветеранів).
- `ROLE_EMPLOYER`: Підприємство або ФОП, що розміщує адаптовані вакансії з менторським супроводом.
- `ROLE_DONOR`: Бізнес чи меценат, що підтримує соціальні ініціативи матеріально або технічно.
- `ROLE_EDUCATOR`: Центр зайнятості або навчальний заклад, що надає ваучери та курси перекваліфікації.

#### Рівень 4. «Координатор аналітики / Адміністратор»
- Управління доступом ОМС до аналітичних зрізів громади.
- Валідація документів партнерів.
- Моніторинг публічного дашборду.

### 1.3. Концепція динамічної еволюції акаунта (Dynamic Role Evolution)

Користувач системи не прив'язується до фіксованої ролі при реєстрації. Впроваджується концепція **контекстного розширення прав**:
1. **Приклад ФОП:** Автослюсар-одинак заходить як Партнер. Він не має найманих працівників, але вмикає статус `ROLE_DONOR` (надає безкоштовне ТО авто для ветеранів). Згодом станція розширюється — він активує статус `ROLE_EMPLOYER` у тому ж кабінеті, підписує типову угоду та публікує вакансію учня автослюсаря.
2. **Приклад Ветерана:** Ветеран після проходження адаптації відкриває власну справу або здобуває юридичну освіту. У власному кабінеті він ініціює перевірку сертифіката і отримує маску `ROLE_SPECIALIST` або `ROLE_DONOR`, залишаючи за собою історію своїх попередніх звернень.

#### Правило активації статусів через підписання документів:
- **Меморандум про взаєморозуміння (Електронний підпис КЕП / Дія.Підпис):** Обов'язковий для інформаційних партнерів, ГО, БФ та публічних каталогів.
- **Угода про співпрацю / Договір про надання послуг:** Обов'язковий для фахівців, які ведуть справи ветеранів, та роботодавців, які публікують вакансії.
- **Блокуючий захист:** Якщо статус обрано в UI, але документ не підписано цифровим підписом — профіль партнера у відповідній категорії залишається неактивним (Draft) і не виводиться в публічний пошук.

### 2.1. Чотири сценарії авторизації (Інклюзивний вхід)

```
                       ┌───────────────────────────────┐
                       │  Точка авторизації на сайті   │
                       └──────────────┬────────────────┘
                                      │
        ┌───────────────────┬─────────┴─────────┬───────────────────┐
        ▼                   ▼                   ▼                   ▼
1. Telegram Widget   2. Phone Gate       3. Дія.Підпис       4. ЦНАП / Простір
   (Смартфони,          (IVR-дзвінок        (Для юристів,       (Особистий прийом,
    1-клік без          з клавішею 1         партнерів та        офлайн-кейс від
    паролів)            або Flash-call)      ОМС)                імені ветерана)
```

1. **Telegram Login Widget (Для смартфонів):**
   - Фронтенд ініціює офіційний скрипт `telegram-widget.js`.
   - Payload: `{ id, first_name, username, auth_date, hash }`.
   - Бекенд валідує `hash` за допомогою SHA256 бота. Створюється JWT сесія.
2. **Безпарольний вхід за номером телефону (IVR / Flash-Call):**
   - Користувач вводить номер `+380XXXXXXXXX`.
   - **Сценарій А (IVR-виклик для аналогових/кнопочних телефонів):** Робот телефонує на номер, відтворює голосове повідомлення: *«Вітаємо на платформі Новий Шлях. Якщо це ви намагаєтесь увійти на сайт, будь ласка, натисніть 1 на телефоні. Якщо ні — покладіть слухавку»*. При отриманні DTMF-сигналу "1" веб-сокет або лонг-полінг на сторінці миттєво авторизує сесію.
   - **Сценарій Б (OTP / Flash-call):** Відправка 4-значного одноразового коду або дзвінок, де кодом є останні 4 цифри номера, що телефонував.
3. **Авторизація через Дія (Дія.Підпис):**
   - Використовується насамперед для партнерів, роботодавців, фахівців супроводу для однозначної ідентифікації посадових осіб та підписання договорів.
4. **Аналоговий вхід через посередника (ЦНАП / Ветеранський простір):**
   - Працівник ЦНАП у своєму робочому кабінеті обирає «Зареєструвати аналоговий кейс».
   - Вносить ім'я/позивний, контактний телефон (за наявності або телефон родича) та опис потреби. Створюється внутрішній профіль, прив'язаний до ЦНАП-координатора.

                     ┌───────────┴───────────┐

            [Авторизація успішна]   як Гість]

#### Правила редіректів та збереження контексту:
- **Intended Destination Storage:** Якщо неавторизований користувач натиснув дію на сторінці `/catalog.html?specialist_id=42`, після успішної авторизації він **НЕ викидається на порожню головну сторінку**.
- Система виконує редірект назад на ту саму позицію сторінки, автоматично відкриваючи картку звернення.
- При прямому вході через кнопку «Увійти»:
  - Користувач з роллю `Ветеран` ➔ перенаправлення на `/cabinet.html#overview`.
  - Користувач з активною партнерською роллю ➔ перенаправлення на `/cabinet.html#partner-workspace`.

## 3. ЛОГІКА ІНТЕГРАЦІЇ З CRM ТА ЖИТТЄВИЙ ЦИКЛ ДАНИХ

### 3.1. Механізм «Прихованого містка» (Session Stitching / Anonymous Merge)

Система трекає подорож користувача на етапі Гостя виключно для адаптації інтерфейсу та знеособленої аналітики, без продажу третім сторонам.

```
БРАУЗЕР (Гість)                           БЕКЕНД / CRM
      │                                         │
      ├──── 1. Запит сторінки ─────────────────►│
      │◄─── 2. Cookie: anon_session_id=XYZ ─────┤
      │                                         │
      ├──── 3. Події кліків та переглядів ─────►│ [Збереження у тимчасовий
      │     (Канів, Психолог, ВЛК)              │  буфер session_events]
      │                                         │
      ├──── 4. Авторизація (Telegram ID: 9988) ─►│
      │                                         │
      ├──── 5. ПОДІЯ MERGE (XYZ + 9988) ───────►│ [Склеювання: історія XYZ
      │                                         │  прив'язується до профілю 9988]
```

#### Схема передачі події склеювання (Payload Specification):
```json
{
  "event": "AUTH_SESSION_MERGE",
  "timestamp": "2026-09-08T01:30:00.000Z",
  "anonymous_token": "sess_anon_9f83a2c1b8",
  "authenticated_user": {
    "user_id": "usr_vtr_550e8400",
    "auth_provider": "telegram",
    "identifier": "tg_77123456"
  },
  "client_context": {
    "geo_community": "Канівська ТГ",
    "user_agent_category": "mobile",
    "landing_page": "/catalog.html?cat=psychology"
  }
}
```

### 3.2. Кейс-менеджмент: Модель Offer/Accept та каскад КАТОТТГ

Передача справи ветерана від координатора або платформи до приватного фахівця pro-bono будується за моделлю взаємної згоди, щоб уникнути психологічної травматизації ветерана у разі відмови.

```
[Ветеран подає запит]
         │
         ▼
[Формування Анонімного Тікета] (Суть проблеми, громада, статус УБД/родина, БЕЗ ПІБ і телефону)
         │
         ▼
[Push/Email/Telegram-пропозиція фахівцю: "Новий кейс pro-bono у Каневі"]
         │
    ┌────┴────────────────────────┐
    ▼                             ▼
[ПРИЙНЯТИ КЕЙС]              [ВІДХИЛИТИ] (Фахівець зайнятий)
    │                             │
    ▼                             ▼
[Встановлення зв'язку]       [Система автоматично передає пропозицію
- Фахівець отримує доступ     наступному фахівцю за каскадом КАТОТТГ
  до контактів та сейфу       або повертає штатному фахівцю ЦНАП]
- Ветеран бачить статус:     (Ветеран не отримує негативної відмови,
  "Фахівець взяв у роботу"    а бачить статус "Підбір спеціаліста")
```

#### Всеукраїнський Каскад КАТОТТГ та Інтерактивна Мапа (Zero Dead-End Guarantee):
Система спроєктована на **масштаб усієї держави (до найменшого села України)**, а не лише пілотних 4 громад:
1. **Рівень 1 (Локальний):** Село / селище / місто ветерана (пряма прив'язка до координат на інтерактивній мапі).
2. **Рівень 2 (Територіальна громада — ТГ):** Фахівці та простори ТГ (1469 громад України).
3. **Рівень 3 (Районний):** Фахівці сусідніх громад та районного центру.
4. **Рівень 4 (Обласний):** Обласні центри та профільні хаби.
5. **Рівень 5 (Всеукраїнський Онлайн / Світ):** Верифіковані фахівці, які працюють дистанційно (Zoom, Telegram, телефон) з будь-якої точки України чи з-за кордону.
*Гарантія відсутності глухого кута:* Якщо у конкретному селі на даний момент 0 фізичних кабінетів, ветеран **ніколи не бачить порожній екран**, а автоматично отримує доступ до онлайн-фахівців та найближчих центрів допомоги на інтерактивній мапі з радіусом доїзду.

### 3.3. REST API Контракти взаємодії Frontend ↔ CRM/Backend

Всі запити здійснюються за стандартом JSON API з обов'язковим передаванням сесійного токена.

## 4. АРХІТЕКТУРА БЕЗПЕКИ ТА ЗАХИСТУ ДАНИХ

### 4.1. Чек-ліст безпеки фронтенду (Frontend Security Checklist)

- [x] **Zero Plaintext Tokens:** Жодних `jwt_access_token` у `localStorage`. Токени авторизації зберігаються виключно в **Secure, HttpOnly, SameSite=Strict** cookies.
- [x] **XSS Prevention (DOMPurify):** Будь-який користувацький контент (опис тікета, повідомлення, коментарі) проходить санітизацію перед рендерингом у DOM.
- [x] **DOM Scraping Protection:** Прямі телефони та email фахівців **НЕ ПРИСУТНІ** в HTML розмітці для неавторизованих сесій. Їх немає у прихованих атрибутах `data-phone="..."` або стилях `display:none`. Контакти надходять від API виключно після успішної перевірки прав.
- [x] **CSRF Protection:** Всі мутуючі запити (`POST`, `PUT`, `DELETE`) супроводжуються валідацією `X-CSRF-Token` заголовка.
- [x] **Content Security Policy (CSP):** Суворі правила для завантаження зовнішніх скриптів (дозволені тільки Telegram Login Widget, Дія та внутрішній домен порталу).

### 4.2. Модуль «Захищений сейф документів» (Granular Vault Security)

Ветеран може зберігати скани своїх чутливих документів (посвідчення УБД, довідки про поранення, постанови ВЛК) у захищеному сховищі без ризику публічного витоку.

#### Схема доступу за принципом найменших привілеїв (Need-to-Know):
1. **Ізоляція файлу:** Файл завантажується, шифрується на серверному боці (AES-256) та отримує анонімний UUID.
2. **Нульовий доступ за замовчуванням:** Жоден фахівець чи адміністратор порталу не має доступу до документів ветерана.
3. **Гранулярний разовий дозвіл (Explicit Ticket Consent):**
   - При подачі заявки до юриста система запитує чекбоксом:  
     *«Надати юристу [Ім'я] доступ до файлу "Постанова_ВЛК.pdf" виключно на час ведення цієї справи?»*
   - Якщо чекбокс активовано, створюється тимчасовий дозвіл `document_grants`, дійсний до закриття тікета або натискання кнопки SOS.
4. **Автоматичне відкликання:** Після завершення консультації або натискання SOS доступ фахівця до файлу анулюється на рівні файлового контролера.

### 4.3. Алгоритм роботи «Кнопки SOS» (Миттєве скасування зв'язку)

Якщо ветеран відчуває дискомфорт або неетичну поведінку під час спілкування з фахівцем:
1. **Тригер дії:** Ветеран натискає червону кнопку **«Припинити роботу з фахівцем»** у картці справи.
2. **Миттєва дія на рівні коду (0 затримки):**
   - Доступ призначеного фахівця до чату, телефонного контакту та файлів сейфа **блокується негайно** (інвалідація токена доступу до тікета).
   - Фахівець бачить системне повідомлення: *«Кейс закрито користувачем»* (без розкриття конфіденційних деталей).
3. **Діагностичне м'яке опитування (User Care):**
   - Ветерану виводиться турботливе вікно: *«Ми зупинили доступ фахівця до ваших даних. Чи бажаєте ви, щоб ми підібрали іншого спеціаліста з цього питання?»*.
   - Фіксація причини (для внутрішнього контролю якості ГО «Талан ЮА» без публікації).
4. **Автоматичний ре-ассайн:** Створюється новий тікет з успадкуванням історії пошуку, який пропонується іншому спеціалісту або передається черговому координатору організації.
5. **Вплив на рейтинг та індекс надійності фахівця (Trust Score):**
   - Натискання кнопки SOS фіксується у картці фахівця та безпосередньо знижує його внутрішній рейтинг надійності.
   - **Диференціація за причинами:** Якщо обрано причину «Неетична поведінка / психологічний тиск» — штраф до рейтингу максимальний; якщо «Вирішив самостійно» — нейтральний закритий кейс.
   - **Тригер антикризової модерації ГО (Правило 2 сигналів):** Отримання 2 скарг поспіль автоматично блокує можливість фахівця отримувати нові звернення ветеранів та генерує сповіщення координатору ГО «Талан ЮА» для ручної перевірки.

### 4.4. Протокол «Грантової заморозки» (De-commercialization Enforcement)

Відповідно до грантової політики МФВ «Відродження» та вимог ГО «Талан ЮА»:
- У коді фронтенду та бекенду **заборонені будь-які комерційні атрибути**:
  - Відсутні змінні або класи з назвами: `pricing`, `tariff`, `commission`, `stripe`, `payment_gateway`, `billing_plan`, `invoice`.

- Комерційний функціонал винесено за межі робочого репозиторію.

## 5. АНАЛІТИКА, МОНІТОРИНГ ЄМНОСТІ ГРОМАД ТА PUBLIC DASHBOARD

### 5.1. Модуль оцінки балансу ємності громади (Capacity Deficit Engine)

Система не просто збирає кліки, а рахує реальний дефіцит соціальних послуг у кожній із 4 цільових громад (Черкаси, Канів, Сміла, Золотоноша).

#### Формула розрахунку дефіциту ємності:
$$\text{Deficit} = \text{Demand} - (\text{Capacity}_{\text{State}} + \text{Capacity}_{\text{ProBono}})$$

де:
- $\text{Demand}$: Кількість унікальних запитів ветеранів у громаді за категорією (наприклад, юридичний супровід ВЛК) за звітний період.
- $\text{Capacity}_{\text{State}}$: Пропускна спроможність штатних державних працівників супроводу (фахівці ЦНАП, соцзахисту, які отримують зарплату з бюджету).
- $\text{Capacity}_{\text{ProBono}}$: Сумарний ліміт прийнятих безоплатних звернень від приватних фахівців та партнерських ГО.

Дані агрегуються та вивантажуються у захищений звіт для міських голів (ОМС) для обґрунтування відкриття нових ставок ветеранських координаторів.

На головній сторінці порталу рендериться публічний віджет для громади та донора (МФВ «Відродження»).
- **Оновлення:** Раз на добу (або кешований Webhook).
- **Метрики віджета:**
  1. *Надано безкоштовних консультацій:* `[Загальна кількість закритих тікетів]`.
  2. *Громад на зв'язку:* `[4 ключові + область]`.
  3. *Партнерів у системі:* `[ГО + БФ + Державні установи + Роботодавці]`.
  4. *Доступних навчальних програм:* `[Кількість активних ваучерів/курсів]`.

## 7. КРИТЕРІЇ ПРИЙОМУ ТА ВАЛІДАЦІЇ (ACCEPTANCE CRITERIA)

Перед переходом до кожного наступного кроку кодогенерації модель Gemini 3.7 повинна перевіряти відповідність наступним критеріям:
1. **Чистота коду:** Відсутність будь-яких комерційних полів, відсутність хардкоду токенів.
2. **WCAG 2.1 Інклюзивність:** Всі кнопки, модальні вікна та перемикачі повинні підтримувати навігацію з клавіатури (`Tab`, `Enter`, `Esc`), мати коректні ARIA-атрибути (`aria-expanded`, `aria-modal`, `role="dialog"`).
3. **Graceful Degradation:** Якщо у користувача відключено JavaScript або заблоковано Telegram-віджет, система повинна виводити альтернативну опцію телефонного входу та аналогового запису через ЦНАП.
4. **Консистентність локалізації:** Інтерфейс створюється українською мовою з повною готовністю до перемикання на англійську (двомовність за грантовою угодою).
